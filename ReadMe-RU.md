# Loadout ModSync

[English](README.md) · [日本語版](ReadMe-JP.md)

[Скачать EXE](https://github.com/succifuys/Loadout-ModSync/releases/download/v0.1.3/Loadout-ModSync.exe) | [v0.1.3](https://github.com/succifuys/Loadout-ModSync/releases/tag/v0.1.3)

Loadout ModSync — лаунчер для Windows и дополнение к **Project Zomboid ДЕДИКАТЕД Server**. Сервер качает моды из Steam Workshop через SteamCMD. Абоненты сервера получают ту версию модов, с которой запущен сервер, а не воркшопа.

Если разраб выкатил обнову, а сервер не ребутался, то абоненты всё равно могут зайти с нужными файлами. Не надо по кругу перезаходить, отписываться от модов и качать всю сборку заново. **При первом запуске сборку всё равно нужно скачать.** Потом лаунчер берёт только файлы, которых не хватает или которые изменились. Если поменялся один файл в одном моде, докачивается этот файл, а не весь мод или модпак.

Ниже инструкция для версии **0.1.3**. Проверяли клиент на Windows и сервер на **Build 42.22.2**. Для других сборок PZ и образов Docker совместимость не обещаю.

## АБОНЕНТАМ (Игрокам)

Понадобятся Project Zomboid в Steam той же версии, что на сервере, лаунчер для Windows x64 и **адрес** ModSync'а от админа. Этот адрес нужен для скачивания модов. **Адрес и порт для входа в саму игру нужны отдельно.**

1. Возьми готовую сборку для Windows x64 у админа или в **Releases**, если она там есть. Архив с исходниками для игры не нужен.
2. Если дали один `Loadout-ModSync.exe`, просто запускай. Если дали папочную сборку, распакуй **весь ZIP** и запусти `DNTSNE-ModSync.exe`. `_internal` оставь рядом: без неё эта версия не заведётся.
3. Запусти Steam. Подключись к Tailscale-сети админа. Radmin VPN и обычный публичный IP этот клиент для скачивания не принимает, тут открывашкой портов не отделаешься. **Закрой Project Zomboid перед обновлением модов.**
4. Открой **Settings**. В **Tailscale server URL** укажи адрес, который дал админ, например `http://100.64.0.1:8787` (IP тут для примера). В **Game folder** выбери папку установленной игры, если лаунчер не нашёл её сам. В Steam её можно открыть через свойства игры: **Установленные файлы → Обзор**. Там короче разберешся как путь копировать из проводника, я в тебя верю. Ну или админ ссам скинет зипку с лаунчером где уже все готово.
5. **Mod folder** лучше оставить как есть. По умолчанию моды идут в отдельную папочку: `%LOCALAPPDATA%\DNTSNE\ModSync\game-profile\mods`. Указывать в пути для установки модов папку SteamWorkshop **НЕ НАДО**, ДУРЕНЬ. Нажми **Save**.
6. Нажми **Synchronize** и жди пока не напишет или не выдаст ошибку я хз. На первом запуске дай лаунчеру скачать и проверить сборку. Нужен запас места. Сколько конкретно? Спроси у админа, сколько весит модпак, и оставь ещё место для временных файлов.
7. Нажми **Launch Project Zomboid**. Для этой сборки запускай игру **НЕ ИЗ СТИМА**. В меню самой игры подключись по адресу и порту, которые дал админ. Если игра всё равно ругается на моды, закрой её и запусти **Settings → Full verification (reads every file)**. Папку целиком не сноси: там могут быть файлы, которые ты добавлял сам.

Лаунчер не меняет подписки в Workshop и не обновляет сам Project Zomboid. Если версия игры не совпадает, переключи или обнови её в Steam, ну или админ глупи у него спрашивай :3 Обычный запуск через Steam работает, если хочется поиграть в ваниллу или с модами из воркшопа то просто из стима игру запускай и не е*и себе мозги. Не пытайся запустить два лаунчера они друг друга побьют и умрут, могут еще чет поломать.

### ЕСЛИ НЕ РАБОТАЕТ

Обычно ошибка бывает на серверной части, по не загрузке модов, или разнице версий игры, что решается обновлением версии, либо у абонента в стиме, либо у админа в штанах.

Не работает?:
Исходники у тебя есть, просто спроси чатгпт или клауд.

## ЛАРПЕРАМ (Админам)
### Что куда ставить

| Место | Что работает |
| --- | --- |
| HOST | Официальный Dedicated Server пакет пятерочки внутри совместимого Docker-образа и его обычный SteamCMD/WorkshopManager. |
| HOST | Mod Sync API в отдельном Compose-проекте и наблюдатель `dntsne-monitor` как служба systemd. Наблюдатель смотрит, что запущено; api отдаёт проверенные файлы. |
| CLIENT | Лаунчер. А чему тут еще работать?|

Пример из репозитория рассчитан на **Linux с Docker Compose и systemd**. Он зависит от устройства конкретного образа PZ: нужны его `/scripts/config/main.py`, WorkshopManager и штатный `/scripts/init-server.sh`. Это **не** готовая замена Compose-файла для любого сервера. Если у тебя Windows Dedicated Server, другой образ или сервер без Docker, не копируй этот пример на живой мир. Сначала адаптируй и проверь отдельно.

### 1. Подготовь тестовый сервер

- Сделай резервную копию **мира, серверного INI и Compose**, когда игровой сервер остановлен штатно. На уже работающем сервере сначала предупреди игроков, сделай сохранение и дождись завершения после `save` и `quit` через свой RCON. Не убивай контейнер, пока идёт запись мира.
- Для первой проверки используй отдельный контейнер и отдельную копию мира. Не подключай один и тот же каталог сохранений к двум работающим серверам.
- В примере хост хранит игру под `/srv/servers/pz`, данные под `/srv/servers/pz/data`, а файлы Workshop под `/srv/servers/pz/workshop`. API и его файлы лежат в `/opt/dntsne-modsync`. Замени примерные пути на свои согласованно во всех файлах, которые их используют.
- Проверь `dntsne/host_monitor.py` и `deploy/dntsne-monitor.service`: в текущем коде по умолчанию контейнер называется `pz-server`, проверяется игровой порт `16261`, а INI читается из `data/Server/DNTSNE.ini`. Для другого имени INI или порта понадобится изменить наблюдатель, а параметрами `--root` и `--container` можно указать свой корень и контейнер.

### 2. Подключи локальные моды к PZ

1. Возьми исходники Mod Sync. Проверь `deploy/compose.pz.override.example.yaml` и сделай свою копию override для **существующего** Compose. Пример подключает подготовленные моды как папку только для чтения. Папка `workshop/.dntsne-local-mods` должна существовать до подключения. Локальные файлы ссылаются на те же данные, что и файлы Workshop, поэтому они должны быть на одной файловой системе.
2. Сохрани оригинальный `/scripts/init-server.sh` **из того же Docker-образа и версии**, не меняя его. Сделай отдельную копию лаунчера: пример override ждёт её даже без Java-агента. Из корня исходников:

```bash
python3 deploy/patch-pz-init.py /path/to/original-init-server.sh /path/to/dntsne-init.sh
```

   Если скрипт не узнаёт исходный launcher, не обходи проверку: адаптируй override под свой образ. Пример `DNTSNE_JAVA_AGENT` для ZombieBuddy закомментирован. Включай его только если он нужен сборке и путь к JAR верный. Оригинальный игровой JAR заменять не надо.

3. В настройках запуска **не удаляй `WORKSHOP_ITEMS`**: это список числовых Workshop ID для SteamCMD. Для списка включённых модов и карт держи правильные `MODS` (Mod ID) и `MAP`. Они не равны Workshop ID. После подготовки в **итоговом INI игры** должно быть пусто именно в строке `WorkshopItems=`. Тогда игра не заставляет клиентов брать другую версию из Workshop, а берёт локальные папки. Проверь, что `Mods=` и `Map=` по-прежнему верные.
4. Проверь итоговый Compose перед запуском. Например, из каталога игрового проекта, подставив реальные имена файлов:

```bash
docker compose -f compose.yaml -f compose.modsync.override.yaml config --quiet
```

   Перед запуском установи файлы в `/opt/dntsne-modsync` по следующему шагу. Затем применяй эти же Compose-файлы на тестовом сервере. Сначала убедись, что сам PZ загружается, нужные моды и карты работают, а тестовый мир открывается. Интеграция с PZ делается отдельно: установщик API её за тебя не включает.

### 3. Установи наблюдатель и API

Сверь путь к папке Workshop в `deploy/compose.modsync.yaml`. Для наблюдателя нужен Python 3.10+ на хосте. Установщик сначала поднимает API на `127.0.0.1` с выключенной раздачей. Tailscale IP задашь ниже. Сам игровой порт и RCON не относятся к API. Не открывай RCON наружу ради синхронизации.

На чистой машине, после проверки файлов и путей, из корня исходников:

```bash
sudo sh scripts/install-server.sh --approved
```

Скрипт копирует файлы в `/opt/dntsne-modsync`, ставит службу наблюдателя и запускает отдельный Compose с API. Он не меняет INI и не перезапускает PZ. При уже существующей установке скрипт остановится: не сноси её для обновления, сначала сохрани настройки и сравни версии файлов. Для первого теста можно оставить раздачу закрытой.

Проверь условия распространения **каждого** мода до того, как начнёшь раздавать сборку. Частная сеть не заменяет разрешение автора. Если раздача допустима, в установленном `/opt/dntsne-modsync/.env` укажи `DNTSNE_LICENSES_APPROVED=1` и `DNTSNE_BIND_IP` со своим Tailscale IPv4, ограничь права на файл и запусти API с этим файлом:

```bash
sudo chmod 600 /opt/dntsne-modsync/.env
sudo docker compose --env-file /opt/dntsne-modsync/.env \
  -f /opt/dntsne-modsync/deploy/compose.modsync.yaml up -d --build
```

С других машин сервер должен быть доступен только тем, кого ты пустил в приватную сеть. Не считай проверку файлов заменой контролю доступа. В публичный репозиторий и Releases **не клади** файлы Workshop, мир, реальные конфиги, токены и пароли.

### 4. Проверь цепочку от сервера до игрока

Проверяй с машины в той же сети, заменив IP в примере на адрес сервера в Tailscale:

```bash
curl -fsS http://100.64.0.1:8787/api/v1/status
```

Нужен `"state":"ready"`, версия PZ и значение `revision`. Если API отвечает, но не готов, посмотри журнал наблюдателя и API:

```bash
sudo journalctl -u dntsne-monitor -n 80 --no-pager
sudo docker compose --env-file /opt/dntsne-modsync/.env \
  -f /opt/dntsne-modsync/deploy/compose.modsync.yaml logs --tail=80 modsync
```

1. На чистом профиле проведи первую синхронизацию и попробуй зайти в тестовый мир.
2. Нажми **Synchronize** второй раз без изменений. Повторного скачивания быть не должно.
3. На тестовом хосте обнови один мод, штатно перезапусти PZ, дождись `ready` и проверь объём реально скачанных данных.
4. Проверь вход в игру после обновления. Если что-то не так, не переноси настройки на живой мир. Вернуть старую схему проще из копии Compose, скриптов и INI; новые сохранения не затирай старым бэкапом без отдельной проверки.

### Как обновляются моды

SteamCMD обновляет Workshop при подготовке запуска PZ. **Не обновляй активную папку Workshop вручную, пока PZ работает**: запущенная игра и папка локальных модов могут читать те же файлы. Останови игру штатно, обнови сборку при следующем запуске и дождись готовности API. Игроки нажмут **Synchronize** перед входом. Перезапуск игрового сервера для обновления модов никуда не исчезает; убираем лишние перезаходы и повторные загрузки у игроков.

API сверяет набор с текущим запуском игры. Лаунчер сравнивает список файлов и контрольные суммы. Если при перезапуске номер сборки поменялся, а файлы те же, заново качать их не надо. Если раздача ещё обновляется или недоступна, подожди, а не подставляй вручную другую версию мода.

Проверено на 0.1.3: повторная синхронизация без изменений на рабочей сборке; первоначальная установка на том же профиле завершилась на 0.1.2; обновление одного файла проверено отдельно на тестовом наборе. Реальное обновление одного мода через Workshop и вход после него ещё нужно проверить на тестовом сервере.

## Разработка и планы

Чтобы запустить клиент из исходников в PowerShell, из корня проекта:

```powershell
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-client.lock
.\.venv\Scripts\python.exe client_app.py
```

Нужен Python **3.12+**; используй версию, для которой устанавливаются зависимости из lock-файла. Для тестов поставь также зависимости из `requirements-server.lock` и `pytest httpx`, затем запусти `.\.venv\Scripts\python.exe -m pytest`. Чтобы собрать Windows-пакет, используй `scripts/build-client.ps1`. Результат будет в `dist/0.1.3/DNTSNE-ModSync`. Упаковывай всю папку вместе с `_internal`, а не только EXE. Для одного EXE без `_internal` запусти `.\scripts\build-exe.ps1`. [Какие ZIP выходят и где лежат](docs/BUILD.md).
